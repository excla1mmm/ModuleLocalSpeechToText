# ModuleLocalSpeechToText

Модуль локальной транскрибации для MikoPBX.

`ModuleLocalSpeechToText` оставляет записи разговоров внутри PBX, создает локальную очередь транскрибации и передает распознавание внешнему worker-у на Apple Silicon. Модуль отвечает за REST API на стороне PBX, сканирование очереди, управление ключами worker-ов, хранение транскриптов, integration events и интерфейс администратора.

Текущая версия модуля: `1.10`.

## Возможности

- Сканирует завершенные CDR и создает задания транскрибации для доступных записей в monitor-директории MikoPBX.
- Отдает файл записи только тому worker-у, которому сейчас назначено задание.
- Позволяет выбрать модель Whisper, языковую подсказку, лимиты очереди, таймаут обработки, словари терминов и пользовательские термины.
- Генерирует ограниченные Bearer API keys для внешних worker-ов.
- Показывает статус worker-а, IP-адрес, runtime-модель, привязанный API key и время последней активности.
- Сохраняет сегменты транскрипта, определенный язык, длительность, использованную модель и технические метрики worker-а.
- Применяет серверный фильтр качества транскрипта, который обрезает или отклоняет очевидные hallucination-артефакты перед сохранением.
- Показывает транскрипты как диалог, включая отдельные колонки левого и правого каналов для stereo-записей.
- Отображает состояние очереди, отложенных записей, пропущенных записей, worker-ов, транскриптов и логов в интерфейсе MikoPBX.
- Публикует идемпотентные события `transcript.completed` для downstream-модулей, включая `ModuleAISupervisor`.

## Архитектура

У решения две части:

1. PBX-модуль: устанавливается в `Extensions/ModuleLocalSpeechToText`.
2. Внешний worker: отдельный процесс на macOS Apple Silicon, который опрашивает PBX API, скачивает назначенное аудио, запускает локальную Whisper-транскрибацию и отправляет результат обратно.

Сам PBX-модуль не запускает Whisper. Он хранит задания в SQLite и стримит запись только после того, как задание забрал авторизованный worker.

## Worker Очереди PBX

`Modules\ModuleLocalSpeechToText\Lib\WorkerCreateTranscriptionJobs` регистрируется через `LocalSpeechToTextConf::getModuleWorkers()`.

Worker периодически сканирует завершенные CDR с записями и создает один `m_STTJob` на путь записи. Дубликаты предотвращаются уникальным индексом `file_path`. Если CDR уже завершен, но файл записи еще не доступен для чтения, запись попадает в буфер отложенных записей и проверяется повторно. Слишком большие или окончательно отсутствующие записи сохраняются как пропущенные, чтобы администратор видел причину отсутствия задания.

Задания в обработке закрепляются за worker-ом как lease. Если worker перестает обновлять lease, зависшие задания возвращаются в `pending` после настроенного таймаута обработки.

## Фильтр Качества Транскрипта

Сегменты от worker-а нормализуются к integer-таймкодам в миллисекундах и проходят через `TranscriptQualityFilter` перед сохранением. Фильтр удаляет пустой текст и типичные hallucination-паттерны Whisper:

- слишком плотный текст для длительности сегмента;
- повторы токенов, фраз, подстрок или символов;
- поток пунктуации;
- replacement characters;
- распространенные маркеры субтитров или хвоста видео.

Когда возможно, фильтр обрезает повторяющиеся префиксы или суффиксы вместо отклонения всего сегмента. Статистика фильтра добавляется в `technical_info.quality` и `technical_info.server_quality`, чтобы в карточке транскрипта было видно, сколько сегментов принято, обрезано или отклонено сервером.

## Интерфейс Администратора

Главная страница модуля состоит из шести вкладок:

- `Настройки`: языковая подсказка, интервал опроса, максимальный размер записи, лимит CDR за проход, таймаут обработки, предустановленные словари и пользовательские термины.
- `Маркетплейс моделей`: встроенные и пользовательские Hugging Face WhisperKit/Core ML модели, ярлыки, runtime ID и выбранная модель.
- `Очередь`: счетчики pending, processing, done today, errors, отложенных записей и пропущенных записей.
- `Воркеры`: сгенерированные API keys worker-ов и зарегистрированные worker-ы с IP-адресом, статусом, привязанным ключом, моделью и последней активностью.
- `Транскрипты`: список последних транскриптов с фильтром по дате и переходом к просмотру диалога.
- `Логирование`: агрегированные последние логи модуля с быстрыми фильтрами по времени.

Карточка диалога показывает метаданные записи, ссылки на прослушивание и скачивание, если запись еще доступна, таймлайн транскрипта, колонки спикеров и техническую информацию, отправленную worker-ом. Для отображения playback-ссылок модуль умеет безопасно находить raw monitor path и соответствующие файлы `pretty-monitor` после проверки через `realpath`.

## Сценарий Установки Worker-А

1. Откройте страницу модуля в MikoPBX.
2. Перейдите на вкладку `Воркеры`.
3. Сгенерируйте API key для worker-а.
4. Скопируйте сгенерированный API key worker-а.
5. Вставьте PBX URL и API key в macOS-приложение worker-а, затем зарегистрируйте этот Mac.

Сгенерированные ключи сохраняются как обычные MikoPBX REST API keys с ограниченными правами только на этот модуль. Worker привязывается к API key, который использовался при регистрации; последующие действия с заданиями должны выполняться тем же ключом.

## API Worker-А

Базовый путь:

```text
/pbxcore/api/v3/module-local-speech-to-text
```

Эндпоинты:

- `POST /workers:register`
- `GET /jobs:getNext?worker_uid=...`
- `GET /jobs/{job_id}:download?worker_uid=...`
- `POST /jobs/{job_id}:heartbeat`
- `POST /jobs/{job_id}:submitResult`
- `POST /jobs/{job_id}:submitError`

Все JSON-эндпоинты используют стандартную обертку MikoPBX REST v3 `PBXApiResult` и защищены правилами localhost или Bearer token.

`jobs:getNext` возвращает:

- `id`
- `call_id`
- `file_url`
- `language_hint`
- `model_id`
- `model_repo`
- `model_engine`
- `model_artifact_type`
- `whisperkit_model`
- `model_display_name`
- `model_source_url`
- `vocabulary_terms`

Внешний worker должен использовать `whisperkit_model` или `model_id` как имя модели WhisperKit, `model_repo` как Core ML репозиторий для ленивой локальной загрузки модели и добавлять `vocabulary_terms` в контекст распознавания. Marketplace-записи сохраняют в payload реальные имена Hugging Face репозитория и папки модели. Пользовательские записи marketplace должны указывать на Hugging Face репозитории, совместимые с WhisperKit/Core ML.

`download`, `heartbeat`, `submitResult` и `submitError` проверяют, что задание все еще находится в состоянии `processing` и назначено именно запрашивающему worker-у.

## Payload Результата

`submitResult` требует:

- `worker_uid`
- `lease_token`
- `transcript` с integer-таймкодами сегментов `start_ms` и `end_ms`

Необязательные поля:

- `language`
- `duration_ms`
- `model_used`
- `technical_info`

Все таймкоды между worker-ом и PBX передаются в integer-миллисекундах. PBX переводит их в секунды только для поля длительности в БД и отображения в UI.

`technical_info` сохраняется как JSON и отображается в карточке транскрипта. Поле предназначено для диагностики worker-а: длительность входного файла, статистика VAD, выбранная модель, голоса языков, отклоненные сегменты, время команд и real-time factor. Серверный фильтр качества добавляет собственные счетчики, не удаляя diagnostics от worker-а.

## Integration API

Модуль предоставляет read-only endpoint-ы завершенных транскриптов для других локальных модулей:

- `GET /transcripts?limit=50&offset=0&date_from=YYYY-MM-DD&date_to=YYYY-MM-DD`
- `GET /transcripts/{result_id}`
- `GET /transcripts/events?cursor=created_at:event_id&limit=100`

Список транскриптов возвращает только компактные summary-данные. Детальная карточка возвращает нормализованные raw-сегменты со стабильными `segment_id` в формате `stt:{result_id}:{index}`, а также читаемые объединенные `turns` и plain `text` для модулей-потребителей, которым не нужны низкоуровневые STT-куски.

Endpoint событий читает идемпотентные события `transcript.completed` из outbox-таблицы `m_STTTranscriptEvent`, поэтому потребитель может сохранить `next_cursor` и продолжить чтение событий позже. События сохраняют `result_id`, `job_id` и `call_id`, когда эти данные доступны. Summary может восстанавливаться не только из job, но и из event/CDR lookup, что помогает интеграциям со старыми строками с неполной job-метадатой.

Эти endpoint-ы используют стандартную обертку MikoPBX REST v3 `PBXApiResult`; новые модули должны использовать их вместо прямого чтения таблиц.

## Таблицы Данных

Модуль хранит состояние в таблицах:

- `m_STTSetting`: настройки модуля, выбранная модель, словари, курсоры очереди и id API keys worker-ов.
- `m_STTWorker`: идентификатор worker-а, статус, IP, модель, привязка к API key и timestamp heartbeat-а.
- `m_STTJob`: очередь транскрибации.
- `m_STTResult`: JSON транскрипта и необязательный технический отчет.
- `m_STTTranscriptEvent`: integration outbox событий по завершенным транскриптам.

## Примечания

- Записи отдаются только из monitor-директории MikoPBX после проверки через `realpath`.
- Настроенный максимальный размер записи проверяется и при создании задания, и при скачивании файла worker-ом.
- Модуль поддерживает несколько API keys для worker-ов, но один API key не может быть привязан к нескольким worker UID.
- macOS-приложение worker-а выпускается отдельно от PBX-модуля.
